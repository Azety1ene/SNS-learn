# ADR-0001: 設計判断を ADR として記録する

- 状態: 承認
- 日付: 2026-10-23

## 背景

- このプロジェクトの最大の目的は学習。「何を作ったか」だけでなく「なぜそうしたか」を後から読めることが大切
- Claude の作業セッションは毎回まっさらな状態から始まる。判断の経緯を文書に残さないと、同じ議論を繰り返したり、理由を知らずに方針を崩したりしてしまう

## 決定

- 大事な設計判断は `docs/adr/` に、1 つの判断につき 1 ファイルで記録する
- ファイル名は `連番-内容.md`（例: `0002-tech-stack.md`）
- 書く項目: 状態、日付、背景、決定、理由、影響（良い点と注意点）、検討した他の案
- 状態は「提案」「承認」「置き換え済み」のいずれか
- 方針を変えるときは古い ADR を書き換えず、新しい ADR を書いて、古いものを「置き換え済み（ADR-xxxx）」にする

## 理由

- 決定だけでなく、当時の前提や選ばなかった案も残るので、前提が変わったときに見直しやすい
- 学習ノートから ADR にリンクすれば、実装と判断の理由を行き来しながら学べる

## 影響

良い点

- 判断の理由を後から追える
- 新しいセッションの Claude も、方針を正しく引き継げる

注意点

- 書くのに手間がかかる。小さな判断（ライブラリの細かい設定など）は ADR にせず、PR の説明に書く
