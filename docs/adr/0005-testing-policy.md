# ADR-0005: テスト方針

- 状態: 承認
- 日付: 2026-10-23

## 背景

- 「モックを使わない」「品質を落とさない」が前提
- オーナーはスマホからしか確認できないので、自動テストで品質を守る比重が大きい

## 決定

- 製品コードにモックやダミー実装を入れない
- 自動テストは次の 3 種類
  - **単体テスト**（Vitest）: DB を使わない純粋なロジック（文字数の数え方、入力チェックなど）
  - **結合テスト**（Vitest）: Server Actions や DB の処理を、本物の PostgreSQL に対して実行する
  - **E2E テスト**（Playwright）: 本物のブラウザで画面を操作し、主要な流れ（投稿する、フォローするなど）を確かめる
- DB や自分たちのコードはモックしない。テスト用の PostgreSQL は、Claude の作業環境と CI（GitHub Actions のサービスコンテナ）でそれぞれ起動する
- 例外: Google や GitHub のログイン画面は、ボット対策や 2 段階認証があるため自動テストから操作できない。テストでは、ログイン済みの状態を DB に直接作って代わりにする。本物のログインは、プレビュー環境で手動で確かめる
- 新しい機能やバグの修正には、必ずテストを付ける。CI が通らない PR はマージしない

## 理由

- モックを使ったテストは、本物の DB との違い（制約、トランザクション、SQL の挙動）を見逃す
- 本物の DB でテストすれば、マイグレーションや制約まで含めて確かめられる

## 影響

良い点

- テストが通れば本番でも動く、と信頼しやすい

注意点

- DB を使うテストは遅くなりがち。テストごとにデータを片付ける仕組みを作り、並列で動かす工夫をする
- 外部のログイン画面を通る流れだけは、自動テストで確かめられない
