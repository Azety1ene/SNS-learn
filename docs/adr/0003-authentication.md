# ADR-0003: 認証方式

- 状態: 承認
- 日付: 2026-10-23

## 背景

- できるだけ安全な認証にしたい
- 誰でも登録できる SNS として公開する
- 無料枠だけで運用するので、独自ドメインを持たない。そのため、一般のユーザーにメールを確実に届ける手段がない

## 決定

- ライブラリは Better Auth を使う
- 新規登録とログインは、Google または GitHub の OAuth で行う
- ログイン後にパスキーを追加でき、以降はパスキーでもログインできる
- パスワードは扱わない
- ログイン状態は、DB に保存したセッションと Cookie で管理する
- プレビュー環境では、Better Auth の OAuth Proxy を使い、本番のコールバック URL を経由してログインする

## 理由

### 方式の比較

| 観点 | パスワード | OAuth | パスキー |
| --- | --- | --- | --- |
| 偽サイト対策 | ✕ | ○ | ◎ |
| DB 流出時 | △ | ◎ | ◎ |
| サーバー負荷 | 重い | 軽い | 軽い |
| メール送信 | 必要 | 不要 | 不要 |
| スパム登録 | ✕ | ○ | △ |
| 手軽さ | ○ | ◎ | ○ |

- **パスワード**: 偽サイトに入力されると盗まれる。他のサービスと同じパスワードを使い回す人を狙う攻撃（リスト型攻撃）にも弱い。再設定にはメールが必要。照合の計算が重く（1 回あたり数十〜数百ミリ秒）、ログインを大量に試されるだけで CPU の無料枠（月 4 時間）を使い切られる恐れがある
- **OAuth**: こちらはパスワードを持たないので、流出するものがない。Google 側の 2 段階認証や不審なログインの検知をそのまま利用できる。Google アカウントは大量に作りにくいので、スパム登録の歯止めにもなる
- **パスキー**: ログインがドメインに結びつくので、偽サイトでは原理的に使えない。サーバーには公開鍵しか保存しないので、流出しても悪用できない
- **メールのリンクでログイン**: メール送信が必要なので対象外

「OAuth で登録し、パスキーを追加する」組み合わせにすると、パスワードを持たずに済み、偽サイトにも強く、メールも要らない。

### 実装方法の比較

- **Better Auth（採用）**: OAuth、パスキー、回数制限、セッション管理がそろっていて、利用実績が多く、修正も続いている。データは自分の PostgreSQL に保存されるので、中身を確認できる。Auth.js（旧 NextAuth）は 2025 年に Better Auth のチームへ引き継がれ、新しいプロジェクトには Better Auth が推奨されている
- **自作**: 学びは最も大きいが、セキュリティの落とし穴をすべて自分で塞ぐ必要がある。「できるだけ安全に」という方針と合わない
- **外部の認証サービス（Clerk など）**: 安全で手軽だが、中身が見えないので学びが少ない

ライブラリに任せる部分も、学習ノートで仕組み（Cookie、セッション、CSRF 対策、OAuth の流れ、パスキーの署名）を説明する。

## 影響

良い点

- パスワードを保存しないので、流出したときの被害が小さい
- メール送信が要らず、無料のまま運用できる

注意点

- Google か GitHub のアカウントがない人は登録できない
- 将来、独自ドメインに移ると、パスキーは登録し直しになる（OAuth でログインしてから再登録する）
- OAuth Proxy で使う共通の秘密値を、プレビュー環境にも置くことになる。コードを書くのはオーナーと Claude だけ、という前提で許容する
- Google のログイン設定は、公開前に「本番公開」の状態に切り替える必要がある

## 検討した他の案

- **パスワード＋2 段階認証（TOTP）**: パスワード単独よりは強いが、偽サイトには弱いまま。再設定にはメールが必要
- **自作、外部の認証サービス**: 上の「実装方法の比較」のとおり
